# 能源行业智能运维 Agent

面向光伏 / 储能 / 虚拟电厂场景的 **RAG + Function Calling** 问答 Agent。
不仅能基于运维规程文档回答"该怎么处理"，还能调用业务工具查询设备状态、发电量、实时告警——**两路信息汇合后再生成答案**。

技术栈：Python 3 标准库（零依赖，不需要 pip install 任何包）+ 原生 HTTP 流式接口 + 单页 Web 界面。

---

## 一、快速开始

```bash
cd energy-agent
python run.py
# 打开 http://127.0.0.1:8848
```

**没有 API Key 也能跑完整链路**（Mock 模式：本地 BM25 检索 + 模拟工具数据 + 基于语料组织的答案）。
配置 Key 后自动切换到真模型：

```bash
# Windows
set LLM_API_KEY=sk-xxxx
set LLM_BASE_URL=https://api.deepseek.com/v1
set LLM_MODEL=deepseek-chat
# 可选：配置后自动启用 向量检索 + BM25 混合召回（RRF 融合）
set EMBED_MODEL=text-embedding-v3
```

支持一切 OpenAI 兼容端点：DeepSeek / 通义千问 / 智谱 / Kimi / OpenAI / 本地 vLLM / Ollama。

## 三、链路设计

```
用户提问
  ↓
① RAG 检索    BM25（+ 可选向量）→ RRF 融合 → Top-K → 相关性阈值判定
  ↓              └─ 低于阈值直接拒答，从源头掐断幻觉
② 工具决策    LLM 判断是否需要查实时数据 → 返回 tool_calls
  ↓
③ 工具执行    执行函数 → 结果回灌进 messages（失败时把错误回传，让模型自我纠正）
  ↓              └─ 最多 TOOL_MAX_ROUNDS 轮，防死循环
④ 流式生成    基于"规程原文 + 工具结果"生成答案，要求标注引用编号
  ↓
⑤ 记忆写入    滑动窗口保留最近 N 轮 + 字符预算兜底
```

**关键设计取舍**：工具决策阶段用**非流式**调用（拿到完整 tool_calls 结构），答案生成阶段用**流式**（保证体验）。代价是多一次决策调用；高并发场景可改为流式增量解析 tool_calls。

## 四、面试高频六问 · 标准答法

### Q1：你的 Agent 怎么做任务规划？ReAct 还是 Plan-and-Execute？

> 这个场景我用的是**单步工具调用 + ReAct 思路**，没有上完整的多步规划。
> 原因是业务提问的复杂度是分层的：问"某设备什么状态""发电量多少"属于**单步可解**，一次工具调用就能拿到答案，上 Plan-and-Execute 反而增加延迟和失败点。
> 我的链路是：检索拿到规程依据 → 模型决定要不要查实时数据 → 执行 → 回灌 → 生成。
> 如果后续要接"先查告警列表，再逐个查设备状态，最后给出处置建议"这种多步任务，我会把规划器单独拆出来，让它先产出步骤序列再逐步执行，并且加最大轮数防止死循环——**现在代码里 TOOL_MAX_ROUNDS 就是为这个留的口子**。

### Q2：RAG 召回率怎么优化？切片策略怎么定的？

> 三个层面：
> **切片**：用的递归切分，段落 → 句子 → 硬切三级，400 字符一片、80 字符重叠。重叠是为了防止一句话被切断导致语义丢失；不按固定长度硬切是因为规程文档是结构化的，按段落切能保住"章节-条目"的语义单元。
> **检索**：默认 BM25 关键词检索，配了 embedding 就走混合召回，两路各排各的名，用 **RRF（1/(60+rank)）融合**——选 RRF 而不是加权求和，是因为 BM25 分和余弦分数量纲完全不同，直接加权必须先归一化，而 RRF 只认排名，天然免疫这个问题。
> **优化方向**（现在没做但知道该怎么做）：
> - 查询改写：用户口语化提问，先让 LLM 转成规程术语再检索
> - 小切片检索 + 大切片喂给模型（Small-to-Big），兼顾召回率和上下文完整度
> - 重排（rerank）：粗召 20 条，用 cross-encoder 重排取 Top-4
> - 元数据过滤：按文档类型、电站类型先过滤再检索

### Q3：向量库选的什么？Embedding 模型怎么选？

> 这个项目语料量小，向量是**内存里直接算余弦**，没有上向量库——这个量级上向量库是过度设计。
> 如果要上生产，我会选 Milvus（数据量大、需要分布式）或者 pgvector（团队已经有 PostgreSQL，不想再运维一个组件）。选型逻辑是：**能用已有基础设施就别引入新组件**。
> Embedding 模型选型看中文语义能力，中文场景优先选在中文语料上训过的（bge 系列、通义 text-embedding-v3），而不是直接套 OpenAI 的 ada；选完要在**自己的业务数据上做召回测试**再定，不在公开榜单上选。
> 还有一点：这个项目里**向量是可选的**，没有 API Key 就纯 BM25 跑——因为关键词检索在"设备编号、故障代码"这类精确匹配上其实比向量更准，**混合检索的价值恰恰是互补，不是替代**。

### Q4：Function Calling 怎么设计？失败了怎么办？

> 三个工具：查设备状态、查发电量、查告警列表。每个工具的描述里都写清楚"什么时候该用它"和"参数格式"，因为**模型是靠描述来决定调不调用的**，描述写含糊了会导致漏调。
> 失败处理分三层：
> 1. **参数错**：工具执行时捕获 TypeError，把错误信息作为 tool 结果回传给模型，让它自己纠正参数再来一次——而不是直接抛异常中断对话。
> 2. **工具不存在**：返回结构化错误，同样回传给模型。
> 3. **调用不终止**：设 TOOL_MAX_ROUNDS 上限，超了就强制进入生成阶段。
> 核心思路是：**把错误当成信息回喂给模型，而不是在代码里硬兜**。

### Q5：多轮对话上下文怎么管理？Token 超了怎么处理？

> 现在用的是**滑动窗口 + 硬预算**：保留最近 6 轮，总字符超 6000 就从最早开始丢。
> 为什么不做全量保留？三个原因：token 成本线性上升、长上下文里模型注意力被稀释（"迷失在中间"）、响应变慢。
> 为什么不做摘要？这个场景的问答独立性很强，上一轮的"逆变器故障怎么修"对下一轮的"储能舱温差多少"几乎没有帮助，**摘要的成本换不来收益**。
> 真需要长期记忆时（比如用户偏好、历史处置记录），正确做法是把它们**存成结构化数据按需召回**，而不是塞进上下文——需要什么取什么。

### Q6：幻觉怎么控制？做了评测吗？

> 四道防线，从源头到末端：
> 1. **源头拦截**（最重要）：检索最高分低于阈值就判定"语料中没有依据"，直接拒答，根本不进生成阶段。这一条比任何 prompt 约束都管用——**与其让模型编完再验证，不如在它开口前就不给机会**。
> 2. **Prompt 约束**：明确"仅依据 CONTEXT 作答，不得凭记忆编造参数与阈值"。
> 3. **强制引用**：要求答案标注 [1][2] 编号，答案可追溯到原文，方便人工核验。
> 4. **工具兜底**：涉及实时数据必须调工具，不允许模型自己编数值。
> 评测目前是人工抽检，没有自动化：准备了覆盖"纯检索类 / 工具调用类 / 应拒答类"三类的测试问题集，看召回片段是否命中、拒答是否正确。要上自动化的话，我会做**检索命中率**（Recall@K）和**答案忠实度**（faithfulness，答案中的每个断言能否在原文找到出处）两个指标。
